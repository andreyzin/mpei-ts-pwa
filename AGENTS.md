# Инструкции для проекта

## Цель

Пиши код так, чтобы его было легко читать, тестировать и изменять через полгода. Предпочитай простые, явные решения и маленькие модули. Не добавляй абстракцию без реального повторения или понятной точки расширения.

## Структура

- `frontend/` — клиентское приложение Vite/React/TypeScript.
- `backend/` — API на Python/FastAPI.
- `compose.yaml` — локальная оркестрация сервисов.
- Фронтенд и бэкенд взаимодействуют только через HTTP API, а не через общие внутренние импорты.

## Архитектура и переиспользование

- Держи ответственность каждого модуля узкой: UI, состояние, транспорт, бизнес-правила и конфигурация не должны смешиваться.
- Выноси повторяющуюся логику в именованные функции, хуки, сервисы или компоненты; не копируй блоки кода с небольшими изменениями.
- Не создавай «универсальные» утилиты, которые используются один раз. Абстракция должна уменьшать связанность или дублирование.
- Зависимости передавай явно. Избегай глобального изменяемого состояния и скрытых побочных эффектов.
- Публичные интерфейсы (компоненты, функции, API-схемы) должны быть минимальными и типизированными.
- Ошибки обрабатывай на границе системы: валидируй входные данные, возвращай понятные ошибки, не глуши исключения.

## Качество кода

- Имена должны объяснять смысл, а не реализацию; избегай `data`, `utils`, `handleThing` без контекста.
- Предпочитай ранний возврат глубокой вложенности условий.
- Комментарии объясняют «почему», а не пересказывают код.
- Не оставляй TODO, отладочные `print`/`console.log`, мёртвый код и закомментированные старые реализации.
- Конфигурацию и секреты не храни в исходниках; используй переменные окружения и `.env.example`.
- Новая функциональность должна иметь тесты на основной сценарий и важные ошибки.

## Проверки перед завершением задачи

Запускай проверки изменённой части и исправляй все новые предупреждения:

```sh
cd frontend && npm run lint && npm run build
cd backend && pytest && ruff check .
```

Если проверку невозможно запустить, укажи причину и выполни доступную альтернативную проверку.

## Изменения API

- Документируй endpoint, формат запроса/ответа и ошибки в коде и README, если это публичный контракт.
- Сохраняй обратную совместимость или явно меняй версию/миграцию.
- Не возвращай внутренние исключения, трассировки и секреты клиенту.

## Docker и окружение

- Сохраняй воспроизводимость сборки: фиксируй версии зависимостей и не полагайся на локальные файлы разработчика.
- Docker-образы должны запускаться от минимально необходимых зависимостей; не добавляй инструменты разработки в production-слой.
- Изменения портов, переменных окружения и healthcheck синхронно отражай в `compose.yaml` и README.

## Визуальный дизайн

- Не используй декоративные градиенты, стеклянные карточки, чрезмерные скругления, эмодзи и случайные акцентные цвета только ради «вау-эффекта».
- Сначала проектируй информационную иерархию: один главный сценарий на экран, ясный заголовок, короткие подписи, заметные состояния загрузки/ошибки/пустого результата.
- Используй ограниченную палитру, один акцентный цвет и семантические цвета только для статусов. Контраст и читаемость важнее украшений.
- Не имитируй мобильный интерфейс на десктопе: сохраняй контекст и плотность информации, но адаптируй навигацию и размеры hit-area.
- Предпочитай нативные паттерны и предсказуемую навигацию; названия пунктов должны быть короткими и однозначными.
- Любой визуальный элемент должен отвечать на вопрос «что пользователь сможет сделать или понять благодаря этому?».

### Anti-slop чеклист

Визуальный стиль этого продукта — спокойный редакционный интерфейс расписания, а не типовой SaaS-dashboard. Перед сдачей экрана проверь:

- Нет фиолетово-синих градиентов, glassmorphism, glow-эффектов, декоративных blobs и одинаковых карточек «иконка + заголовок + текст».
- Не используй Inter как бездумный дефолт. Для заголовков выбирай характерный системный/брендовый шрифт, для текста — нейтральный читаемый; решение должно быть зафиксировано в токенах.
- Палитра состоит из фона, поверхности, текста, приглушённого текста, одного акцента и семантических цветов. Акцент не используется на каждом элементе.
- Радиусы, тени и границы образуют ограниченный словарь: одна базовая величина радиуса и максимум два уровня поверхности. Не оборачивай каждый блок в отдельную карточку.
- Иерархия строится размером, весом, интервалом и композицией; не добавляй бейджи и разделители, если они не помогают сканированию.
- Контентный экран должен иметь один главный сценарий и один очевидный следующий шаг. Убирай декоративный текст и повторяющиеся подписи.
- Мобильный layout проектируй для большого пальца и реального контента: нижняя навигация, минимум 44px hit-area, отсутствие горизонтального скролла без явной причины.
- Анимация только объясняет изменение состояния или поддерживает переход; никакого bounce/hover ради украшения.
- Проверка «line-up»: поставь экран рядом с тремя похожими продуктами. Если его нельзя отличить без логотипа, пересмотри типографику, композицию или токены.
